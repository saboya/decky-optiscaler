These headers MUST match the OptiScaler build shipped in bin/. The layout
mirror the ASI uses is generated from Config.h, so a mismatch means the ASI
reads the wrong offsets - it fails its validation checks and stays inert.

The files were moved into subfolders upstream after v0.9.4 and are flattened
here: hooks/FG_Hooks.cpp, menu/menu_common.cpp, upscalers/FeatureProvider_*.cpp
and wrapped/wrapped_swapchain.cpp. Enum types the Config class uses (FSR4Model,
FSR4Support, Upscaler, SharpenShader) are declared in OptiTypes.h, which is not
vendored; scripts/generate_asi_layout.py carries their underlying types.

unordered_dense.h is unchanged: the external/unordered_dense submodule is still
at 73f3cbb237e84d483afafc743f1f14ec53e12314 at this commit.

STATE MIRRORS in asi/live.cpp (state_head, state_frame_head, state_fg_block,
state_tail) are ported to this commit's State.h. What changed since v0.9.4:

  * newBackend and the three *Upscaler Config members are the Upscaler enum, not
    strings; live.cpp maps the host's id strings onto it (OptiTypes.h/.cpp).
  * DeviceAdapterNames is gone, so capturedHudlesses is the first table after
    the head of State and changeBackend the next one. newBackend is an enum and
    cannot tell the two apart any more; order does.
  * fgChanged/scChanged are 22/21 bytes before capturedHudlesses; frameCount is
    16 bytes before changeBackend.
  * The FFX upscaler versions are two FfxVersionList structs (DX12, Vulkan); the
    ASI reads the one State::api selects.
  * skipHeapCapture and creatingD3DDevice are thread_local statics and take no
    room in the object.

Two sizes cannot be read from the headers because they are MSVC standard
library internals: std::mutex (80 bytes) and std::deque (40 bytes). They are
checked against the shipped OptiScaler.dll by scripts/verify_state_layout.py:

  * State::Instance() is the function at RVA 0x2c7e0. The constructor is found by
    its `lastMipBias = 100.0f; lastMipBiasMax = -100.0f` initialisers, which also
    fixes where changeBackend is (+0x628).
  * Every `[reg + disp]` memory operand in .text inside State's range is
    collected -- through ANY register. The first attempt looked only at [rax]
    within a few instructions of a call to Instance(), which is how five members
    came to look "never accessed": the compiler had moved State& into r14/r15/
    rbx/rsi and used it from there. WAR_xefgRequestFGToggle, xefgDynamicCapFps,
    dlssgLastSetMode, lastFGPresentMs and postDone all have accesses of the
    right width at the computed offsets (e.g. `mov byte [r15+0x67c], 1`,
    `movss [r8+0x680], xmm6`, `cmp dword [r15+0x688], 3`, `movsd [r15+0x888],
    xmm0`, `cmp byte [rsi+0x8e0], 0`).
  * 13 of 13 checked members pass. The check can fail: with the deque taken as
    32 or 48 bytes, or the first mutex as 72, a double or the last member lands
    where nothing accesses it and the script reports MISS.

That is evidence, not proof -- an access of the right width at the right offset
is what a correct layout produces, not the only thing that could. Members that
are only touched through helpers would not show up, and the script makes no
claim about those. A different OptiScaler build means running it again.

NOT VERIFIED AT RUN TIME: none of this has been executed inside a game. Every
lookup fails closed -- a State that does not match leaves the feature reporting
unavailable -- but a mirror that matches wrongly would write to the wrong byte.
